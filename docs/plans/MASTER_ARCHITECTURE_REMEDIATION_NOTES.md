## Deviations (planned behavior vs code constraint → decision)

1. **T19.1 actor model:** plan prefers an authenticated-invoker restore with in-SQL actor verification. The Supabase `restore_backup_tx` remains `SECURITY DEFINER` + service_role-only grant with the admin gate enforced in `lib/db/supabase.ts:restoreBackup` (same precedent as the pre-existing service_role-backed restore). An invoker-side `auth.uid()` check is not possible through the service_role path, so authorization stays at the app layer; grants (`revoke ... from public,anon,authenticated` / `grant ... to service_role`), pinned `search_path`, and atomicity tests (`tests/supabase-restore.test.ts`, `tests/supabase-migrations.test.ts`) are the enforcement evidence.
2. **T19.2 Supabase atomicity (superseded by Deviation 29):** the earlier claim → `execute()` → ledger-commit flow with a separate claim row was replaced. Supabase now achieves claim+write+commit in ONE statement transaction via the idempotency triggers (`20260920000000_idempotency_effects.sql`, rewritten in place — never applied to a live project): BEFORE `private.mobile_idempotency_claim` atomically inserts the `idempotency_effects` row (unique `(key, actor_id, operation)` is the linearization point) and raises `23505` (same-payload replay) or `IDEMPOTENCY_CONFLICT` (different payload); AFTER `private.mobile_idempotency_commit` records `response_status` in the same tx. The effect fingerprint is server-derived (`sha256(table+op+row jsonb)`) and `resource_id` binds the row, so caller headers are routing keys only — closing the forged-header false-success path. New stamped deliveries no longer touch `idempotency_keys`; pre-existing ledger rows (`committed_unknown`, old committed rows) are absorbed for the migration window. Legacy ledger-only operations (batch/duplicate) keep the explicit claim/commit path by design (documented in `lib/idempotency.ts`).
3. **T18.2 compare:** plan requires each comparison range to use its own complete/paged range. Implemented via server-side `getReportTotals` per compare period (complete aggregate, not client paging), which is stronger than paging the raw rows.
4. **T18.3 SVG:** plan allows SVG with restricted CSP + verified safe handling, otherwise explicit reject + doc. Chose explicit reject (`ALLOWED_MIME_TYPES` excludes `image/svg+xml`; documented in `lib/branding-proxy.ts`) — remote SVG fails closed to the bundled fallback.
5. **T18.4 proof:** plan requires a server-render dedup proof (a direct getter call is not proof). Added the strongest static evidence available without a full RSC harness: `tests/branding-render-dedup.test.ts` asserts cross-render freshness and intra-render consistency via `react-dom/server`. Single-query dedup across RSC layout passes requires the full Next.js server runtime and remains an open release-evidence gate.

## Intentional Transport Differences (T18.0)

Recorded so unexpected authorization differences stay failing regressions:

1. **Messages/DTO/status:** `app/actions/timesheets.ts` returns `{ error }` strings while `lib/api/v1/services/timesheets.ts` returns `{ code, message, status }` mapped from the same typed domain outcomes (`lib/domain/timesheets.ts`). Byte-identical messages across transports are not required.
2. **Compare ranges:** `app/reports/page.tsx` compare periods use complete server aggregates (`getReportTotals`) rather than paged rows — stronger than per-range paging.
3. **Group-report `co` path:** app-layer treats `co` as see-all while RLS team policies scope them; `co` stays on the existing grouped-totals path pending an explicit RLS policy decision (Deviation 23).
4. **Branding preview:** `GET /api/branding/logo?preview=` accepts a caller-supplied URL but is super-admin-gated and runs the same `fetchSafeImage` SSRF validation as the saved-logo path.
5. **Supabase session lifetimes:** other provider sessions lose refresh immediately (`signOut({ scope: 'others' })`); already-issued provider access JWTs remain valid until the verified 15-minute-or-less expiry.
6. **Offline compatibility:** unkeyed requests execute normally (shipped clients); keyed replays deduplicate per `(key, actor, operation)` with canonical payload fingerprints.
